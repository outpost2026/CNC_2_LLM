## Proč GitHub TEĎ (a ne dřív)

Dosavadní workflow (adhoc adresáře, diff.txt, ruční verzování) FUNGOVALO pro
V2.0–V2.2, kde byl jeden vývojář, jeden monolitický soubor, malá komplexita.

V2.3 přináší:
- 7+ modulů (místo 1 monolitu)
- Testovací sadu (pytest, unit testy, integrační testy)
- Golden mastery pro regresní ochranu
- Epistemický rámec (E_confidence, --strict)
- 6 vývojových fází s 13 tasky

Tato komplexita už vyžaduje verzovací systém. Git není "nice to have" —
je to infrastruktura profesionálního vývoje.

## Jak bude vývoj vypadat s GitHubem

### Standardní workflow pro jeden task (např. P0-01)

```bash
# 1. Vytvoř větev pro task
git checkout -b feature/p0-remove-semantic-layer-mapping

# 2. Implementuj změnu
# ... uprav soubor ...

# 3. Ověř, co jsi změnil
git diff

# 4. Commitni změnu
git add src/dxf_tool_config.json
git commit -m "P0-01: Remove semantic_layer_mapping from tool_config"

# 5. Pushni na GitHub (záloha)
git push -u origin feature/p0-remove-semantic-layer-mapping

# 6. Až jsi hotový, přepni na main a sluč
git checkout main
git merge feature/p0-remove-semantic-layer-mapping

# 7. Pushni main + tag
git push
git tag -a v2.3.0-dev1 -m "V2.3.0-dev1: P0 complete"
git push --tags
```

### Experiment bez rizika

```bash
# Chceš zkusit nový přístup, ale bojíš se rozbít fungující kód?
git checkout -b experiment/alternative-proximity

# ... implementuj experiment ...

# Pokud se nepovedl:
git checkout main
git branch -D experiment/alternative-proximity

# Pokud se povedl:
git checkout main
git merge experiment/alternative-proximity
```

### Návrat k libovolné verzi

```bash
# Zobrazit historii
git log --oneline

# Vrátit se k V2.2.0 (baseline)
git checkout v2.2.0
```

### Záloha před LLM promptem

```bash
# Podle DR2 — před každým promptem na DeepSeek
git add -A
git commit -m "WIP: before DeepSeek prompt for P1-03 proximity_matrix"
```

## Git tahák — 6 příkazů, které potřebuješ

| Příkaz | Co dělá | Kdy použít |
|--------|---------|------------|
| `git status` | Ukáže, co se změnilo | Před každým commitem |
| `git add <file>` | Označí soubor k uložení | Po úpravě souboru |
| `git commit -m "..."` | Uloží změny lokálně | Po dokončení tasku |
| `git push` | Nahraje změny na GitHub | Pro zálohu |
| `git checkout -b <name>` | Vytvoří novou větev | Před novým taskem |
| `git merge <branch>` | Sloučí větev do aktuální | Po dokončení tasku |

To je všechno. Šest příkazů. Zbytek se naučíš za chodu.

## Časté situace a jejich řešení

### "Zapomněl jsem vytvořit branch a už jsem něco změnil"

```bash
git checkout -b feature/muj-task
# změny jdou s tebou do nové větve
```

### "Commitnul jsem špatně, chci to vzít zpátky"

```bash
git reset --soft HEAD~1
# soubory zůstanou změněné, můžeš je znovu commitnout
```

### "Rozbil jsem soubor, chci verzi z posledního commitu"

```bash
git checkout -- src/dxf_tool_config.json
# Vrátí soubor do stavu z posledního commitu
```

### "Chci vidět, co jsem změnil od posledního commitu"

```bash
git diff
```

### "Chci vidět celou historii změn"

```bash
git log --oneline --graph
```

## Co NEDĚLAT s Gitem

- **Nepushovat** `output/`, `__pycache__/`, `.env` — proto máme `.gitignore`
- **Necommitovat** hesla, API klíče, tokeny
- **Nepoužívat** `git push --force` na main (nikdy!)
- **Nemazat** `.git/` adresář (to je celá historie)

## Kdy pushnout na GitHub

Pushovat můžeš:
1. Po každém commitu (automatická záloha)
2. Na konci dne (denní záloha)
3. Před vypnutím počítače (jistota)

GitHub repr je soukromé (private). Nikdo jiný ho nevidí.
Slouží primárně jako:
- Záloha (kdyby selhal disk)
- Historie (co se kdy změnilo)
- Budoucí kolaborace (až bude Odoo tým)

## Shrnutí

GitHub pivot NENÍ:
- Složitý (6 příkazů, 30 minut učení)
- Riskantní (všechno je lokálně, GitHub je jen záloha)
- Předčasný (komplexita V2.3 ho vyžaduje)

GitHub pivot JE:
- Jednorázová investice 3 hodin
- Trvalá ochrana proti ztrátě dat
- Základ pro profesionální CI/CD pipeline
- Nezbytný pro budoucí kolaboraci
